# v81 红球追踪提速与行程修正

## 实机诊断与授权

用户反馈“整个太慢，方向没问题”。读取v80时，available=1、mode=2、有效目标连续存在，MCU最大服务间隔32～34ms。发出的步数采样为 `[-160,-88]`、`[-151,-160]`、`[-160,-95]`、`[-160,-2]`，上下轴反复触及旧±160步边界，左右轴也曾到边界。因此不只是120pps限速，软件行程限制也是不继续移动的原因。

修改前已发s，后续状态mode=0/status=16确认驱动释放。立即停止回复曾读到status=24（短暂尾部保持），未把该瞬时状态误当成重新运行。没有在运行中切换速度。

询问机械余量后，用户明确回复“360°安全”。本轮仅放宽到现有FPGA硬件可接受的±640步，未声称已经覆盖360°；完整角度仍需驱动细分、传动比或实测步数/角度关系。轴0正向朝上、轴1正向朝左沿用实测，不改方向。

## 参数变化

| 项目 | v80 | v81 |
|---|---|---|
| 追踪最高请求速度 | 120pps | 300pps |
| 追踪加减速 | 800pps/s | 1600pps/s |
| 中心误差速度比例 | 2pps/像素 | 3pps/像素 |
| 误差滤波每帧更新 | 差值1/4 | 差值1/2 |
| 追踪软件范围 | ±160步 | ±640步（原FPGA硬范围） |

6像素死区、三帧有效目标后运动、丢球减速待机、目标恢复自动继续、手动停止、MCU100ms停顿保护和FPGA250ms看门狗保留。制动前推距离同步采用新的1600pps/s参数，不只提高速度而漏改制动。速度斜率仍按实际服务间隔计算。

状态新增v0/v1，表示MCU最后请求的两轴速度，不是编码器实测速度。到软范围边界仍禁止继续向外，允许向内退回。x/y单轴测试保留旧80pps，n双轴扫描保留旧200pps；本轮只提高追踪速度。

## 验证结果与边界

- C控制器完整回归：模式、方向、死区、丢球/断流一分钟保持待机、三帧自动恢复、手动停止不复启、时间回绕、10/30ms不等服务间隔、扫描与每轴±640边界/反向退出均通过。测试实际请求峰值达到300pps。
- 新AHB回归核验原硬件能原样接受(+640,-640)目标与(+300,-300)pps提交，ArUco结果发布不受影响，旧AHB分支及步进RTL回归通过。
- 原16组理想视觉模型通过。另12组大偏差模型（初始x232/y42、0.5/1/2像素每步、0/50/100/150ms观测延迟）与SHA核验过的v80控制器对照：稳定时间合计18490→15150ms，平均缩短约18.1%。10组更快，两组高比例/高延迟场景反而更慢（750→1000ms，1420→1580ms），故不能承诺实机所有场景都提速或不摆动；真实机械效果待观察。
- 对照中未出现模型目标因过冲离开视场。模型不包含真实力矩/丢步/机械背隙/识别误检或曝光变化，不作为实机追踪质量证明。
- MCU编译text=29444、data=240、bss=16548、栈预算2048，总预算48280/49152字节，BSS未增加。相对v80多76字节代码；不是运行栈高水位测量。
- FPGA RTL/约束完全不改，复用v77已验证布线。Slice19465/21216（91.75%）、ERAM97、DSP32；SWNS+0.009ns、HWNS+0.020ns。联合镜像FPGA数据区逐字节相同。
- 初次测试包装脚本的Windows路径/正则转义错误导致基线查找失败，未封装/未烧录。修复仅在测试工具，保留失败日志后重跑；新回归通过后才继续封装部署，没有跳过失败。
