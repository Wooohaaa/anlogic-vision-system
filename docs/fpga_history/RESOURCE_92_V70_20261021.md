# v70：恢复整机92%资源门槛

用户将整机目标从20000 Slice恢复为92%以内，即 `floor(21216×0.92)=19518` Slice。v69布局19925，因此至少需要降低407 Slice。v69路由中断未完成，不继续使用该布局烧录。

## 改动

1. `ua_user_algo_96.v`：将RGB的2拍早期延迟及6拍后期延迟改为两个8深度、96位的同步RAM环形延迟。共享3位指针，分别读写间隔1与5，维持原寄存器链的逐拍语义，包括无效拍。仅复位指针/有效标签，不清空RAM；首个有效输出前所需地址均已填充。读写地址不同，不依赖同地址读写模式。保留Sobel、素描、浮雕、卡通、灰度与直通全部模式及原图像尺寸/流水延迟。
2. `ua_stepper_position.v`：位置、目标、速度内部从有符号16位缩至11位，覆盖原±640步、±1000pps范围；对32位总线的两路16位输入先做完整范围检查，再存窄位值和非法标志。非法提交仍关闭并清除原点，不能因截断把32767等非法值变成合法小目标。合法值读回仍符号扩展为两路16位。非法暂存值读回为截断后的符号扩展，不应依赖非法值读回保存原始32位数据；MCU仅提交合法值。
3. 全部原视频功能、降噪强度、手势、ArUco、目标跟踪和电机安全逻辑保留。MCU仍是已编译的v69固件，不增加MCU手势工作，不自动启动电机。

这是存储实现与合法范围位宽优化，不是降分辨率、减帧率或改变图像算法。预计用部分剩余ERAM换取Slice，实际数量必须由TD报告确认。

## 验证与构建

- `python tools/test_algo_v70.py`：七种模式各一帧1280×720、气泡、帧间复位，和改动前独立快照逐拍比较，1612800个有效像素及valid/SOF/EOL/无效拍输出通过。
- `python tools/test_stepper_v70.py`：双轴运动/故障、共享ArUco AHB、历史总线、MCU控制和ArUco运行时五组通过，源码哈希保存在 `tmp/v70_stepper/result.json`。这是RTL/软件模型证据，不是电机实物验收。
- 参考快照保存在 `host/tests/ua_user_algo_v69_reference.v`、`host/tests/ua_stepper_v69_reference.v`，不进入产品综合列表。
- 构建入口 `python tools/deploy_v70.py`。综合布局资源超过19518时立即停止，不进入长时间布线。最终Routed的资源也再次检查19518，ERAM≤108、DSP≤40，SWNS/HWNS非负、STNS/HTNS为零后才允许生成/打包/烧录联合Flash镜像。
- MCU ELF、源码与固件启动CRC校验保持；不复用不匹配的v55 MCU。电机默认OFF，用户已确认尚未接线。下载本身不启动扫描或跟踪。

实测：v70布局20249 Slice、103 ERAM，RAM延迟方案虽然逐拍一致，但整机打包反而变大。92%门槛已阻断后续布线及下载；该RAM延迟改法已撤回，不作为最终优化结果。
